### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program and use it for PR operations the built-in PR tool does not cover, per **Opening a PR**: `gh` by default; use `origin pr ...` only when the `origin` command is available and can resolve this repository, otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Within about 15 minutes, each owner starts an uncommitted `decisions.tsv` trail, pushes its first branch snapshot, and opens the PR ready, never draft, per **Opening a PR**. After that, the owner pushes its branch again after every verifiable unit, with hooks on. A WIP commit is fine. Open the PR before full self-proof so the URL, decisions, and checks form a durable trail. The owner then completes the build, automated-review triage per `../references/bugbot-triage.md`, the available cleanup pass, `.agents/skills/no-comments/SKILL.md`, and the rebase rules below. Keep the trail and return it with the report. Track each spawned agent's ID, expected runtime (at least the longest past run of that kind), and state in an uncommitted `children.tsv`. Rebase once before reporting the code-ready head and starting babysit; keep that merge base during fix rounds. Rebase again during merge prep, or earlier only when `git merge-tree` finds a trunk conflict or CI fails because of a trunk change. When the shipped code is final and cleanup is complete, report the code-ready head SHA; this starts the first verification round before full self-proof. Report the SHA of every later push that changes the patch. In each round, run the owner's real-artifact self-proof (the **prove-it-works** principle skill), CI, and babysit alongside the root's swarm; report owner-ready with the head SHA when all three finish. Before each push that starts a round, run the repository's path-specific pre-review checks on the committed head. A hook pass does not count as proof. Publish each rebase only on the owner's own branch, with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The owner may not merge without Step 4's clean verdict.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Independent PRs branch straight off main; sequenced work is merge-then-branch. Do not register or stack independent PRs with Graphite. One exception: an owner that must split a genuinely dependent change may hold a short private stack.
4. **Swarm-verify every code round.** Start a round at the code-ready head SHA and at every later push that changes the patch. Fan out independent verifiers per the **swarm** skill and aggregate one verdict. Re-run the required gates at that SHA, prove the load-bearing behavior live on the real surface with the active harness's browser, desktop, terminal, or service-control capability, and audit the receipts in the owner-ready report plus the diff. Use at least two audit lanes with distinct focuses, such as caller coverage, races, or data and config safety, and give each the full review brief. Run the same behavior on current trunk as a regression check. If trunk cannot perform the new behavior, record that and verify the new behavior and its final user-visible result on the change. The live lane is required for a clean verdict. Send every proven finding to the owner in one fix-forward. A finding reported as a note still counts. For each behavior defect, require a failing test that covers every affected site, or a reproduction receipt when a test cannot show it. Add the defect to the next round's brief. The owner-ready report is not a verdict. The PR is merge-ready only when the root's clean verdict matches that patch and Step 5's post-rebase checks pass; retain a prior lane result only when `playbooks/shipping.md` says its patch-id still applies.
5. **Prepare and merge only the verified patch, then spawn a fresh owner.** Start merge prep only after the round's lanes have started. Rebase onto current trunk immediately before merging and report the resulting head SHA. CI must pass on that exact head. Compare its base-to-head patch-id with the round's verdict. Once that head is green and its patch-id matches the verdict under `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. Re-verify when the patch changed, unless the shipping playbook preserves a lane's result for a proven test, docs, or lint-only difference. Never use a green check from an older SHA as proof. On a clean result, the owner squash-merges its PR and returns. A fresh owner takes the next self-contained item, per superdev-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict authorizes that merge. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover tool approvals, record that countersign in the format the tool permits and link it to the root's verdict. A lane checks the approval record against the countersign. Never bypass an approval enforced by the forge. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm `/loop 1h` with a prompt that runs this tick. `/loop` works in local and cloud roots. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk with `git show origin/main:.agents/skills/superdev-mode/playbooks/autopilot-full.md` and audit the operation against it. Fix drift during that tick. Probe each owner, collect decision trails, and inspect every `children.tsv`. Judge an owner by the pushed branch and the decision trail that Step 2 requires. Replace an owner whose agent cannot start a turn. Count only side effects as progress: commits, pushes, PR or check deltas, and stored reports. Treat a lane or child that errors or passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement if its work is still needed. Record the stalled child and replacement. If the owner cannot do so, the root handles it. Do not treat a stall as proof or as a reason to drop the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick after delegated work finishes, including work that remains after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
