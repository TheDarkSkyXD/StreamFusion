# Replace per-Kick network-health with a generic per-platform health tracker

`backend/api/platforms/kick/kick-network-health.ts` modelled only local Chromium network/GPU process crashes (filtered out plain timeouts and 5xx as "normal Kick flakiness"). When `api.kick.com` itself goes degraded (mass `TRANSIENT:timeout` and `TRANSIENT:502` during a Kick incident), `fetchKickFollowed` fans out 80+ slug requests, each retries 3× with backoff, and each surfaces a per-slug warn — flooding the log and stalling the followed-streams sidebar for minutes. Twitch had no equivalent module at all.

We're collapsing both concerns under a single `backend/api/unified/platform-health.ts` keyed by `Platform = "twitch" | "kick"` with state `PlatformHealth = "healthy" | "degraded" | "down"`. `degraded` is a rolling failure-rate circuit breaker over remote `TRANSIENT:timeout` / `TRANSIENT:5xx`; `down` preserves the existing short-fuse `net::ERR_*` burst behavior. Callers consult `isPlatformHealthy(platform)` and serve the stale-success cache when unhealthy; transitions fire an IPC event the renderer subscribes to for a degraded-platform banner. The merge is intentional: one health state machine per platform is simpler than three sibling modules (existing kick-network-health + a new kick-outage + a twitch equivalent), avoids double-counting failure signals, and gives Twitch the same instrumentation for free instead of bolting it on later.

Considered and rejected: keeping `kick-network-health.ts` as-is and adding a sibling `platform-outage.ts` that handles the remote-failure-rate concern across both platforms. Cleaner separation of "local-process" vs "remote-platform" failure source, but doubles the API surface every caller has to check and re-introduces the double-count problem (a Chromium crash inflates BOTH counters). The merge is load-bearing — reversing it would touch every call site in `kick/endpoints/`, the renderer banner subscription, and the IPC contract.
