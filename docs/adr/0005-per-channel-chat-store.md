# Per-channel chat message store with dual-shape migration

## Kick return-history amendment

Kick has no supported public API for reading recent live chat. StreamFusion may best-effort seed from Kick's undocumented web endpoint, but that endpoint can fail or change without notice. To preserve honest context when a viewer returns to a Kick Channel, the renderer saves only messages the app actually observed into the existing bounded history LRU before final service release drops the live bucket. Restoration requires an exact Platform, normalized Channel slug, and internal Channel id match; server and cached rows still pass through the per-channel store's id dedupe.

The retained cache is capped at 50 normal, non-deleted messages per Channel, 12 Channels, 1 MB total, and 24 hours. A synchronously readable in-session overlay uses the same bounds so an immediate return does not race the asynchronous disk write. It does not synthesize missed messages or claim complete coverage while the app was disconnected. Twitch remains unchanged. This amends the earlier rejection of retained history without keeping live store buckets across navigation.

The chat store keeps every message in a single flat `state.messages: ChatMessage[]` shared across all chat panels (`apps/desktop/src/store/chat-store.ts`). Every Zustand subscriber that reads `state.messages` re-renders on any add anywhere — so in a 4-panel multiview, one message in Channel A re-renders Channel B's `ChatMessageList`, Channel C's, and Channel D's. A single 100-1200 message cap is also shared across panels (originally sized for the 5 GB-spike incident that the cap mitigated). The shared shape also leaks across other operations: a mod `/clear` in one Twitch panel wipes every Twitch panel's chat (`clearMessages(platform)` filters by platform, not channel), and a global `isPaused` boolean means scrolling up in one panel pauses every panel's auto-scroll. KickTalk's `ChatProvider` stores `messages: { [chatroomId]: Message[] }` keyed per chatroom (`reference/KickTalk-main/.../ChatProvider.jsx:36, :1087-1091`) and avoids all three issues.

We're refactoring the store to `state.messagesByChannel: Record<channelKey, ChatMessage[]>` plus `state.pausedChannels: Set<channelKey>`, where `channelKey = ${platform}:${channelId}` (canonical builder `buildChannelKey(platform, channelId)`). Each channel gets its own cap (default 600, max 1200), its own pause state, its own dedupe window, and its own batch flush timer. Migration is **dual-shape**: both `state.messages` (flat) and `state.messagesByChannel` are written on every add for the duration of the migration. Consumers move PR-by-PR — `ChatMessageList` first (the hot path that delivers the multiview re-render win), then mod actions (`clearMessages` / delete / pause), then chat-history backfill (`prependMessages`), then the final cleanup that deletes `state.messages` and `state.isPaused`. Bucket eviction is tied to chat-service ref-counting: when `kickChatService.release()` / `twitchChatService.release()` brings the count to zero and tears down the WS, the store also drops that channelKey's bucket. A dev-only assertion verifies `state.messages.length === sum(state.messagesByChannel[k].length)` after every add during the migration window.

Considered and rejected:

- **Big-bang refactor in one PR**. Changes every consumer at once with no transitional state. Cleanest end-state but a single regression breaks all chat across both platforms, and the diff is large enough that PR review degrades to rubber-stamping. The dual-shape window adds ~1.2 MB of duplicate message storage at peak — trivial cost for the rollback safety.
- **Nested map `Record<Platform, Record<channelId, ChatMessage[]>>`**. Explicit platform/channel hierarchy and easier clear-by-platform. But every selector and every immutable update needs two-level traversal, and Zustand's shallow-eq comparison gets uglier. The composite-string key is flatter and reads/writes are one indirection.
- **Bare `channelId` (no platform prefix)**. Risky: Twitch broadcaster IDs and Kick chatroom IDs live in independent namespaces and a coincidental collision would silently merge two unrelated chats. The prefix costs nothing.
- **Keep global cap, share buffer across channels with LRU eviction**. Preserves the original RAM-spike mitigation literally but undoes the multiview win — a busy Channel A starves Channel B's scrollback. The original RAM spike was a shared-array pathology, not a per-room one; per-channel caps at 1.2 MB total for a 4-panel multiview don't reproduce the failure mode.
- **Keep global `isPaused`**. Smaller refactor scope but preserves the user-visible multiview bug where pausing one panel freezes all of them. Half-fixing the data shape while leaving the pause shape global wastes most of the UX win.
- **Per-channel pause but hard-delete `state.isPaused` in the same PR**. Cleaner end-state but violates the dual-shape principle: any consumer reading `state.isPaused` would break in the same PR that moved messages, defeating the rollback safety. During migration, `state.isPaused` is a derived boolean `pausedChannels.size > 0`.
- **LRU max-N channel-bucket cap**. Buckets persist across navigation, evicting the least-recently-used when a 9th channel is created — best scrollback UX for users who cycle between a few channels. Rejected for now: bookkeeping (per-channel last-access timestamps), arbitrary cap value to defend, and the service-tied lifecycle already matches today's clear-on-switch behavior. Reconsider if users complain that returning to a recently-visited channel loses scrollback.

Reversal cost is low while the dual-shape window is in effect — every consumer still has `state.messages` available, so a regression in the per-channel path can be unwound by reverting the consumer change and dropping the per-channel reads. Once `state.messages` is deleted in the final cleanup PR, the refactor is no longer trivially reversible; that PR should ship behind a verification pass (multiview render-count benchmark vs. baseline, mod /clear in one panel does not affect others, scrolling up in one panel doesn't pause others). The per-channel cap is a user preference (`chatDisplay.messageLimit`) clamped to `[10, 1200]` in `chat-store.ts:28-30`, so individual channel buffer size remains tunable post-landing without further code changes.
