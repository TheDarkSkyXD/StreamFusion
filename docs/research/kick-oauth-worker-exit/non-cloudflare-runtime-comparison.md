# Non-Cloudflare runtime comparison for Kick OAuth

**Fact check date:** 2026-08-30

**Decision supported:** choose a host for the minimal Kick confidential-client service without changing StreamFusion's built-in sign-in window.

## Result

Three stacks merit a human decision:

1. **AWS Lambda + API Gateway HTTP API + DynamoDB + Secrets Manager** has the clearest fully managed path to a trustworthy source address, an atomic two-counter limiter, immutable releases, and rollback. At low traffic, API and compute usage can remain inside free grants, but Secrets Manager has a small recurring charge and AWS carries the most infrastructure surface.
2. **Google Cloud Run + external Application Load Balancer + Firestore + Secret Manager** also meets the contract with managed services and strong revision rollback. The load balancer is necessary to normalize a trustworthy client-address header; its `$0.025/hour` forwarding-rule charge is about `$18.25` in a 730-hour month before data processing, which dominates this service's low-volume cost.
3. **Vercel Functions + Upstash Redis** is the smallest operational stack. Vercel supplies the trusted source address and deployment rollback, but its native rate limiter cannot key on the hashed code or refresh token. The required Redis dependency is inexpensive at low volume, while production-grade Upstash availability materially raises the cost.

This report does not select among them. Deno Deploy is the closest conditional alternative because Deno KV can implement the limiter without another vendor, but current Deno Deploy documentation does not establish an authoritative original-client address at the function boundary. The other screened runtimes add a decisive rollback, reliability, cost, or state-operations disadvantage without improving the shortlist.

## Contract every candidate must satisfy

The service retains the two current operations and their compatibility boundary:

- `POST /auth/kick/token`
- `POST /auth/kick/refresh`
- the existing request fields, successful response shape, and compatible HTTP/OAuth error meanings

The Electron desktop and planned Android client continue to own browser or popup launch, PKCE, OAuth `state`, callback handling, token storage, and refresh scheduling. A native client calls the service over HTTPS directly, so browser CORS is neither required nor desirable. The service owns `KICK_CLIENT_SECRET`, the explicit redirect allowlist for both native clients, input validation, the call to Kick, response validation and translation, and safe telemetry. This division preserves the built-in Electron popup; replacing the Worker does not move the authorization UI into the service.

The limiting requirement is stricter than the edge-rate-limit features offered by these hosts:

- fixed window, **30 attempts per source address per minute**;
- fixed window, **6 attempts per SHA-256 OAuth subject per minute**;
- both dimensions shared by exchange and refresh;
- no plaintext authorization code or refresh token persisted;
- a limiter read, transaction, or connectivity failure rejects the request before Kick is called.

The OAuth subject is the authorization code on exchange and the refresh token on refresh. The application hashes it before constructing the state key. A time-bucket suffix belongs in both keys, while database TTL is only asynchronous cleanup. The decision must not rely on eventual expiration to decide whether the current window is open.

Provider request throttles can absorb broad abuse, but they do not replace this limiter. For example, API Gateway documents its throttling targets as [best effort rather than guaranteed ceilings](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html), and Vercel's non-Enterprise WAF keys are limited to [IP address or JA4 digest](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting). None of the shortlisted runtime controls derives a SHA-256 key from the relevant JSON body field.

### Runtime-independent implementation conditions

All three stacks still need the same service code safeguards:

1. Parse a small, size-bounded `application/json` body; reject unknown routes, methods, fields, invalid grant shapes, and redirect URIs outside an exact environment-specific allowlist.
2. Obtain the source address only from the platform field or normalized header named above. Never trust a client-supplied forwarding-header prefix.
3. Hash the route's OAuth subject in memory. Execute both fixed-window checks against shared state before reading the client secret or calling Kick. Return `429` for an exceeded limit and a stable `503` for unavailable limiter state.
4. Put an explicit abort deadline around the Kick token request. The platform's overall request deadline is not an upstream timeout. Treat DNS, connection, timeout, malformed JSON, wrong content type, and invalid success or error bodies as bounded stable errors.
5. Set `Cache-Control: no-store` on every response. Do not enable wildcard CORS or generic preflight handling for native callers.
6. Pin builds and dependencies, keep infrastructure and log configuration in version control, deploy a health-checked candidate, and prove rollback before moving production traffic.

## Candidates not advanced

These candidates can run a small HTTPS handler, but each has a decisive disadvantage for this contract.

| Candidate | Reason not advanced |
| --- | --- |
| Azure Functions | Microsoft recommends Flex Consumption for new serverless apps, but Flex has no deployment slots and [rollback means redeploying a previous package](https://learn.microsoft.com/en-us/azure/azure-functions/functions-rollback-deployments). It also requires a storage account, a secret service, and shared rate-limit state. Cosmos DB serverless is pay per request, but [free tier is unavailable for serverless accounts](https://learn.microsoft.com/en-us/azure/cosmos-db/free-tier), and transactional batches are limited to [one logical partition key](https://learn.microsoft.com/en-us/rest/api/cosmos-db/transactional-batch). The resulting state and release design is more involved than AWS without a low-volume advantage. |
| Netlify Functions | Netlify's native rate limiting aggregates only by [`ip` or `domain`](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/), so the subject dimension still needs Redis or another database. Its Free plan provides 300 credits, and [exhausting them suspends all projects on the account](https://www.netlify.com/pricing/). Vercel plus the same managed Redis has a clearer trusted-address contract and rollback story for this use case. |
| Deno Deploy | Deno KV supplies [atomic transactions](https://docs.deno.com/deploy/kv/transactions/) and key expiration inside the platform, making the limiter attractive. Deno Deploy also documents [timeline rollback](https://docs.deno.com/deploy/reference/timelines/) and [integrated logs, traces, and metrics](https://docs.deno.com/deploy/reference/observability/). However, the current Deploy request documentation does not guarantee a provider-authenticated original-client address or header. [`remoteAddr` describes the peer TCP address](https://docs.deno.com/api/deno/~/Deno.ServeHandlerInfo.remoteAddr) in the Deno runtime, which is not sufficient evidence behind hosted ingress. A hard source-address limit cannot rest on an undocumented assumption. The new platform also states that [monorepos are not yet supported in the dashboard](https://docs.deno.com/deploy/getting_started/), and its Free and Pro plans have [no reliability SLA](https://deno.com/deploy/pricing). Reconsider only after provider confirmation or a documented ingress contract. |
| Fly.io | Fly can [auto-start and stop Machines](https://fly.io/docs/launch/autostop-autostart/) for HTTP traffic and offers a [managed Upstash Redis extension](https://fly.io/docs/upstash/redis/), so it is technically possible. Rollback is a redeploy of an earlier image; Fly warns that old images are not retained forever and [configuration and secrets are not rolled back](https://fly.io/docs/blueprints/rollback-guide/). It adds more machine lifecycle and image-retention work than Vercel while retaining the same external Redis dependency. |
| Render | The free web service sleeps after 15 minutes and can take about a minute to restart; Render says [not to use free instances for production](https://render.com/docs/free). Free Key Value is in-memory and loses data whenever it restarts, so it cannot enforce the fail-closed shared limiter. A paid web service plus [paid persistent Key Value](https://render.com/docs/key-value) is credible, and Render has artifact rollback, but it introduces an always-on cost floor without a compensating contract advantage. |
| Railway | Railway can host the handler, but its Redis template is explicitly [unmanaged](https://docs.railway.com/databases/redis): backups, monitoring, security, and maintenance belong to StreamFusion. [Hobby has a `$5` minimum and seven-day logs](https://railway.com/pricing), while rollback images are retained for [only 72 hours on Hobby](https://docs.railway.com/reference/deployments#deployment-actions). Owning limiter-database operations is out of proportion to this narrow service. |

Cloud Run functions were not scored separately from Cloud Run because second-generation functions use the Cloud Run infrastructure and do not change the shared-state or trusted-source-address requirements. Netlify Edge Functions were likewise not scored separately: moving the handler to an edge runtime does not add a subject-derived shared limiter.

## Decision points for the architecture ticket

[Choose the replacement Kick auth runtime](https://github.com/TheDarkSkyXD/StreamFusion/issues/118) can decide among the shortlist by resolving four explicit tradeoffs:

- Is the roughly `$18.25/month` documented Google load-balancer floor acceptable in exchange for a single-cloud managed stack?
- Is AWS's additional infrastructure-as-code surface acceptable for its atomic DynamoDB design and mature alias rollback?
- Is a second vendor in the token path acceptable, and if so, is best-effort/free Upstash reliability sufficient or must the production pack be budgeted?
- Should Deno receive a small documentation-support inquiry or ingress prototype, or is the undocumented source-address boundary enough to exclude it now?

Whichever stack is selected, the implementation specification should name the exact state schema, transaction, IP trust rule, timeout, error map, secret-access policy, log fields, alerts, deployment gate, rollback command, and a native-client contract test run from both Electron and Android-shaped callers.
